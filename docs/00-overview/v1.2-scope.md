# V1.2 Scope

**Status:** Living document, ported to Elite-Intel — tracks what **Elite-Intel V1.2** contains as scope decisions are confirmed.

**BindForge is not versioned separately** (settled 2026-09-08). It is a part of Elite-Intel, released on Elite-Intel's schedule, so it has no version of its own. The "v1" language throughout this documentation set is inherited from EDO StellarCore, where BindForge was a plugin with an independent release cadence. That is no longer true, and a second version number would only invite the question of which BindForge belongs in which Elite-Intel. Distinct from [conflicts-and-open-questions.md](conflicts-and-open-questions.md), which tracks disagreements between source documents; this tracks forward decisions made after this documentation package was built.

---

## Build/Ship Order

BindForge and StarVizion are being built as features of **Elite-Intel**, which already ships. There is no separate host to build and no combined "platform v1" to ship alongside them — each feature lands on its own schedule, as a contribution to an existing application (see [Elite-Intel Platform Map](../01-host-integration/elite-intel-platform-map.md)).

**Build order:** BindForge first, in **V1.2**. It is the more design-complete of the two, it has substantial existing code in `elite.intel.ai.hands` to grow from, and Elite-Intel already ships a Bindings section that BindForge grows out of — so it has a concrete, already-wanted destination in the app.

**StarVizion is TBD** (settled 2026-09-08). It comes after BindForge, and whether it lands in V1.2 or a later release depends on how BindForge goes and on what Alan and Krondor work out. Its scope is settled and recorded below; its release is not.

### Phased rollout — revised 2026-09-08

**BindForge upgrades the existing Bindings section rather than replacing it.** It is not a new top-level section, and there is nothing to decommission.

The existing section already has BindForge's shape. Two of its parts are renamed and grown; two are added.

| Today | Becomes | |
|---|---|---|
| **Bindings** (main tab) | **BindForge** | renamed last, once the section is what the name says |
| Binding Profile (sub-tab) | **Bind Editor** | grown first, renamed when it holds its modes |
| Binding Management (sub-tab) | **File Manager** | grown first, renamed when it holds all three sub-tabs |
| — | **Alias Designer** | new |
| — | **Preset Editor** | new |

**Game Install Locations is not a top-level sub-tab.** It sits inside File Manager alongside Player Backups
and Edit History — see [File Manager](../02-features/bindforge/file-manager.md#game-install-locations).

**The naming rule: a tab is named when it becomes what the name says** (settled 2026-09-09). A new tab
arrives under its final name because it is that thing from the moment it exists. An existing tab keeps its
current name until it has grown into the new one. No tab ever carries a name that promises more than it
holds.

| # | Phase | Notes |

### The BindForge name is returning, not arriving

**Recorded 2026-09-09, because this is the kind of context that disappears and leaves people puzzled by a
tab name.**

BindForge was already the tab's name in Elite-Intel during earlier collaboration. **Alan asked Krondor to
change it to "Bindings" before v1.1 shipped**, specifically so the BindForge name would not go out attached
to a bind editor that was not yet BindForge. The editor at that point was nowhere near what the name was
meant to describe, and shipping the name anyway would have spent it.

So phase 4 is not a rebrand of somebody else's feature. **It is the same naming rule as every other phase
in this table, applied once already** — the name was withheld until the thing deserved it, and it comes
back when it does. That earlier period is also why `BindingManagementPanel`'s javadoc still opens with
*"the Binding Management sub-tab of BIND FORGE"*.

**Why this replaced the earlier plan.** The 2026-09-01 decision was to build BindForge *alongside* the existing editor and remove the old one at a sixth phase, with a system property
(`elite.intel.bindeditor.enabled`) hiding the old tab during development. That was right when it was made: the existing editor was thinner and the collision risk looked higher.

It stopped being right because **Krondor kept building.** The Bindings section now has conflict detection with severity tiers, reserved-key rules, in-game control names, search, a keyboard availability map, the working-copy and apply pipeline, and player backups with restore. Building separately now would mean reimplementing three weeks of his work in order to delete it later.

It is also what the project's own standard requires: `CODING_STANDARD.md` lists *"add a second way to do something the codebase already does one way"* as a design anti-pattern, and two bind editors is the textbook case.

**The system property was reverted 2026-09-08** and no longer exists. It protected other users from a half-built parallel editor; with the upgrade happening in place and only Alan and Krondor running it, there is nobody to protect.

### The code stays where it is — stated by Krondor 2026-09-12

**No class, package or file in the bindings code is renamed, moved or repackaged during V1.2
development.** `elite.intel.ai.hands` keeps its name and its contents; `BindingsTabPanel`,
`BindingProfilePanel`, `BindingConflictRules` and the rest keep theirs. Growing a class is fine —
moving one is not.

> *"As you work on V1.2 we will be adding bug fixes and new rules as we discover them. It would be
> easier to merge changes if the current bindings editor, detection and rules logic remain in the
> same packages with the same classes… For now let's try to minimize merging nightmare."*

**Why it matters more than tidiness.** V1.1 is a rolling release with real users, and Krondor ships
binding fixes and new collision rules weekly — to the same classes BindForge is being grown out of.
He merges master into `V1.2-BindForge` himself. A rename converts each of his incoming fixes into a
manual conflict, and the real risk is not the merge going badly, it is **silently dropping a rule he
already shipped to users.** The September conflict work
([three blocking rules now](../02-features/bindforge/domain-knowledge/EliteDangerous-ConflictRules.md#the-three-breaks-in-the-context-model))
is exactly the kind of change that must keep arriving cleanly.

**Phase 4 is unaffected, because it renames labels and not code.** The BindForge rename is three keys
across nine `gui*.properties` bundles. No class is called `Bindings*` because of what the tab says.

Refactoring is deferred, not forbidden: naming can be revisited well before the V1.2 release, once
the two lines of work are no longer landing in the same files every week.

Work lands on the `V1.2-BindForge` branch; Krondor merges into `V1.2`.

## CAPI Integration

Out of scope entirely. Neither BindForge nor StarVizion has any CAPI dependency — its only consumer was
[FlightDeck](../04-other-ideas/FlightDeck.md), which is not being built.

## Host Prerequisites (Elite-Intel)

There is no service set to build — Elite-Intel supplies most of it already. What V1.2 actually requires from the host is the short list of **gaps** identified in the [Elite-Intel Platform Map](../01-host-integration/elite-intel-platform-map.md#service-map):

| Gap | Needed by | Blocking? |
|---|---|---|
| Archive backup / restore (ZIP) | BindForge File Manager | Yes, for File Manager |
| Game-install discovery per storefront | BindForge Device Identity + Button Map domains | Yes, for those two domains |
| A status-badge affordance on tabs | BindForge error surfacing | Degradable — an alternative signal could serve |
| Keyboard/mouse input source | StarVizion keyboard Vizlets | Yes, for those node types only |

Everything else the specs assume — device input, path resolution, settings persistence, logging — already exists.

**One thing to check before building any panel** (carried from the punch list, 2026-09-09): confirm the
UI component set available from Gnevko's V1.1 interface redesign — tables, tabs, toggle chips, sliders,
the capture-flow visuals. BindForge's screens should be assembled from what the application already has
rather than introducing a parallel set, which is the same *"no second way to do something"* rule that
decided the upgrade-in-place question.

## BindForge

V1.2 requires all of the following **fully functional**, not partial/placeholder:

- **Alias Designer** — see [Alias Designer](../02-features/bindforge/alias-designer.md)
- **Bind Editor — Game Mode** — see [Bind Editor](../02-features/bindforge/bind-editor.md#game-mode)
- **Bind Editor — Action Groups** (named "Purpose Mode" in earlier docs) — **promoted into scope.** Previously documented as deferred; now required. See note below.
- **Bind Editor — Input Mode** — **promoted into scope, and now fully designed** (press a physical input, see everything bound to it across all sections, edit right from there — see [Bind Editor — Input Mode](../02-features/bindforge/bind-editor.md#input-mode)). Not to be confused with Control Types, which is a related but distinct idea and remains out of scope (see below).
- **Bind Editor — Anomalies** — a dedicated mode gathering the four kinds of binding that will not do what the commander expects: reserved keys, missing controls, conflicts, and contextually invalid bindings. Named "Conflicts" until 2026-09-07, when it outgrew the word — see [Bind Editor — Anomalies](../02-features/bindforge/bind-editor.md#anomalies).
- **Bind Editor — Capture Dialog** — every mode that lets the player rebind something (Game Mode, Action Groups, Input Mode, Anomalies) now uses one single, consistent capture mechanic: a floating dialog modeled on the base game's own rebind popup, never a mode-specific variant — see [Bind Editor — Binding Editor Panel](../02-features/bindforge/bind-editor.md#binding-editor-panel--capture-dialog).
- **Shared conflict detection ("Conflicts finder")** — see [Bind Editor — Shared Conflict Detection](../02-features/bindforge/bind-editor.md#shared-conflict-detection)
- **Preset Editor** — see [Preset Editor](../02-features/bindforge/preset-editor.md)
- **File Manager** — see [File Manager](../02-features/bindforge/file-manager.md)

**Not in V1.2:** Control Types (named "Type Mode" in earlier docs; remains parked — see [Bind Editor — Control Types](../02-features/bindforge/bind-editor.md#control-types)), Controller Mode (remains a back-burner idea).

## StarVizion — release TBD

**Scope confirmed; release undecided (2026-09-08).** StarVizion comes after BindForge. Whether it lands in V1.2 or a later Elite-Intel release depends on how BindForge goes. The feature list below is settled — the schedule is not, so nothing here should be read as a V1.2 commitment.

Its first release requires:

- **Vizlets, the NeuroNode system, and StarCalc** — core, required, unchanged from how they're already documented.
- **All 8 NeuroNode primitives** (Dot, Bar, Line, Arc, Text, Grid, Bitmap, Parametric) — all required, not a partial set.
- **HoloFrames** (named VizLoadout for most of this documentation pass before being renamed) — required, including automatic mode-based switching between them — previously a later idea, now promoted. See [HoloFrames and Persistence](../02-features/starvizion/holoframes-and-persistence.md).
- **Mode-Based Visibility** (per-Vizlet) — required.
- **VR Overlay**, all four render modes — Desktop, VR, Desktop + VR, and the Windows-only Desktop+ hybrid mode that hands VR placement to an external tool — all required. See [VR Overlay](../02-features/starvizion/vr-overlay.md).
- **Frame-rate input polling** — provided by Elite-Intel's `elite.intel.devices` at ~60 Hz, as shared infrastructure StarVizion consumes rather than builds. Note the divergence: the package *pushes* delta events and keeps no queryable snapshot, so StarVizion maintains its own current-value cache. **Global keyboard capture is NOT provided** — `DeviceService` covers joysticks, HOTAS, gamepads and pedals only. Keyboard Vizlets need a source that does not yet exist. See [Device Input](../01-host-integration/elite-intel-platform-map.md#device-input).

**Not in StarVizion's first release:** CortexUnit (reusable/shareable Vizlet templates) — confirmed wanted, but its own design hasn't started yet; Vizlet-wide shared locals (Option A vs. B still undecided); Journal/CAPI telemetry bindings; multi-game support. See [StarVizion Roadmap](../02-features/starvizion/roadmap.md).

**Progress toward the prerequisite breakdown:** the foundational "what is a Vizlet actually made of" work flagged in [conflict 2.1](conflicts-and-open-questions.md#21-cortexunit-reusableshareable-vizlet-template--confirmed-wanted-confirmed-low-priority) is well underway. Confirmed so far:

- NeuroNode modes are renamed **Live** / **Static** (formerly Reactive/Decoration).
- The Vizlet authoring workflow is **NeuroNode-first, bind-on-demand** — a NeuroNode is added and visually designed before any input is chosen, and picking an input source is only required at the point the user decides that NeuroNode should become Live (see [Vizlets and the Node System — Authoring Workflow](../02-features/starvizion/vizlet-and-node-system.md#authoring-workflow-neuronode-first-bind-on-demand)).
- **A Vizlet is not a typed object.** There is no "stick Vizlet" or "throttle Vizlet" category — a Vizlet is just a named container of NeuroNodes, and its name/tags are author-chosen descriptive metadata with no enforced meaning. This directly informed the Editor's design: it must be structurally identical for every Vizlet, regardless of contents.
- **The Vizlet Editor is now built out in the mockup** — two top-level tabs, switched right below the editor's back button/title, with nothing shared between them: **Vizlet** (Identity, Window, Render Mode, Mode-Based Visibility — everything about the Vizlet as a whole; opens by default) and **NeuroNodes** (Canvas, Node Stack Panel, Property Panel, Device Input Monitor, Input Simulation Panel — the NeuroNode-composition workspace). The Vizlet tab consolidates three previously-undocumented-in-the-UI settings groups (window properties, VR render mode, mode-based visibility) that were each already specified in prose but had no UI home until now. See [UI Layout — Vizlet Editor](../02-features/starvizion/ui-layout.md#vizlet-editor).
- NeuroNode deletion, Vizlet deletion, HoloFrame deletion, and Vizlet import are all implemented in the mockup and documented.
- **Adding a NeuroNode creates a generic, type-unassigned node** — the user then picks a primitive type (Dot, Bar, Line, Arc, Text, Grid, Bitmap, Parametric) from the Property Panel before any other property appears. All 8 primitives from [Vizlets and the Node System](../02-features/starvizion/vizlet-and-node-system.md#primitives) are now selectable and produce a working illustration in the mockup's canvas, not just Dot and Grid.
- **NeuroNode reordering is implemented** — drag-and-drop within the Node Stack Panel; the node dragged to the top of the list renders frontmost (highest Z). A new NeuroNode is inserted directly above whichever one was selected when it was added.
- **NeuroNodes are now individually nameable** directly from the Node Stack Panel row, not just via the Vizlet's own Identity fields — expected to matter once a Vizlet accumulates many NeuroNodes.
- **Still open:** only one example Vizlet ("Right Stick") is wired up with real NeuroNode data in the mockup; the other two library cards don't open the editor yet. Since the editor is now confirmed structurally uniform, extending this to the other cards is mechanical, not a design question — just not done yet.
